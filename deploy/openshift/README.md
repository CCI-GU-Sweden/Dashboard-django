# OpenShift test deployment

For the planned move to the existing bookmarked test address and eventual
production release, see [DASHBOARD-CUTOVER.md](DASHBOARD-CUTOVER.md). The
original initial-deployment instructions below contain historical assumptions
and must not be applied over the running cluster without review.

These manifests prepare an **isolated test deployment of the Django foundation**. They do not deploy the existing Express dashboard's features and must not replace its Service or Route. They have not been tested on your cluster. Resource names are fixed to `dashboard-django`; use a separate project or review naming collisions first. Console labels can vary by OpenShift version and role.

For the planned test in `core-omero-test`, inspection of the `dashboard-test` Deployment showed its database variables reference the `filestatistics-app-credentials` Secret. A read-only query found its connection uses database `omerofilestats`, role `filestats_dashboard`, and schema `public`; that role cannot create tables in that schema. The web Deployment references those same keys, while the migration Job uses the same host, port and database but takes its user and password from `filestatistics-pg15-credentials`. The migration credentials' target and permissions are not yet verified and those credentials were exposed and need rotation. The proposed Route is `https://dashboard-django-test.apps.k8s.gu.se/`, with the requested IP allowlist already in `04-app.yaml`. This short hostname has not been checked or created: confirm that cluster Route policy, DNS and the default certificate allow it. If it is changed, update both host values in `02-config.yaml`, the Route host in `04-app.yaml`, and the registered ORCID callback together. Nothing has been deployed by these instructions.

## Before starting

- Choose a test project, test hostname and Route access controls with the platform team. A Route can be reachable from the internet as soon as it exists: provision an approved restriction **before** creating it. The application is not ready for public use.
- Confirm that your project allows Git builds, access to GitHub and the image registry, pulling the Dockerfile base image and installing Python packages during a build. Private Git requires an approved build source secret. The Git ref must already be pushed; use an immutable reviewed commit SHA.
- The migration Job and web Deployment use different database credentials. Confirm with the database owner that the selected migration identity can connect to the dashboard's target database and create Django tables in `public`, and coordinate rotation of credentials previously exposed in chat. After migration, the owner must grant the runtime role `filestats_dashboard` the required access to the new Django tables and sequences; the migration role's ownership does not automatically grant access to the runtime role. A read-only inventory found no tables with prefixes `auth_`, `django_`, `account_`, `socialaccount_` or `accounts_` in the current schema at the time of inspection; recheck before migrating if the schema changes. **Do not run this against production or change collector-owned tables without a reviewed plan.** A backup and restore procedure are required even on a shared test database.
- Register an ORCID sandbox client with exact callback `https://dashboard-django-test.apps.k8s.gu.se/accounts/orcid/login/callback/` if the proposed host is accepted. Use its client ID and secret below; sandbox and production identities/credentials are separate.
- The supplied Route annotation includes `10.250.0.225/27`, which describes the entire `10.250.0.224/27` subnet, not just `.225`. Verify that this whole range is intended and that the router accepts the supplied CIDR format. Verify the allowlist is enforced using both allowed and disallowed source networks; VPN, load balancers and proxies may affect the source address seen by the router. ORCID returns users through their browser, so the browser's source must also be allowed.
- Confirm the Route terminates HTTPS and the router strips untrusted client-supplied `X-Forwarded-Proto` and sets a trustworthy value. Only then enable `DJANGO_TRUST_PROXY_HTTPS`. Without this Django cannot reliably recognize HTTPS behind an edge Route, causing redirects or CSRF failures. If the platform cannot guarantee header trust, use an approved alternative architecture rather than enabling it blindly. Confirm network policies and TLS requirements for PostgreSQL and ORCID with the platform/database owners; these files do not establish database TLS or network isolation.
- Confirm the test hostname is permitted, the cluster can issue/use an appropriate Route certificate, the CPU metrics API and quota are available, and the internal image registry is accessible to application pods. The default Route certificate may not cover an arbitrary hostname.

## Web console: initial release

Select the correct **Project** in every screen. Use the console's **+ / Import YAML** or equivalent YAML editor to paste each file. `kind: List` files create their listed resources; if your console does not support creating a List, create each item separately. These are ordinary resources, not automatically processed templates: edit every `REPLACE_WITH_...` value before creating them. Do not paste filled secrets into an issue or repository.

1. **Create the build.** Configure the webhook Secret and `01-build.yaml` as described in the cutover guide. In **Builds → BuildConfigs**, open `dashboard-django`, start a build, and wait for **Complete**. Inspect its logs, source revision and resulting `dashboard-django:candidate` ImageStreamTag. GitHub pushes can trigger builds once the webhook is installed; promotion to the Deployment remains manual.
2. **Find the image digest.** In the ImageStream/tag details or its YAML, find the built image's internal registry `dockerImageReference` including `@sha256:...` (typically in the tag's `status.tags[].items[]`). Copy the full digest reference. If the console does not show it, the CLI alternative is `oc -n YOUR_PROJECT get is dashboard-django -o yaml`. Use the same digest for the migration and the application; do not use the mutable `candidate` tag for either release step. Check that the ImageStream belongs to the chosen project.
3. **Set non-secret configuration.** In `02-config.yaml`, check that the proposed hostname is accepted, or replace it in both values with the accepted test Route hostname. Keep `dashboard-probe.local` in `DJANGO_ALLOWED_HOSTS` for internal probes. After the forwarded-header check above, change `DJANGO_TRUST_PROXY_HTTPS` to `1`; create the ConfigMap. Its environment variables are read at pod startup, so later changes require a controlled rollout.
4. **Create the app Secret.** Under **Workloads → Secrets**, create the generic/Opaque Secret `dashboard-django-app` using the keys in `secrets.example.yaml`: `DJANGO_SECRET_KEY`, `ORCID_CLIENT_ID`, and `ORCID_CLIENT_SECRET`. Enter values directly in the console. Generate a new Django key through your approved secret-management process; neither the existing API token nor its JWT secret is a Django or ORCID credential. The manifests reference the five database keys already used by the running dashboard. Do not commit values or copy production credentials into test.
5. **Run migrations once.** Edit `03-migration-job.yaml`: replace the release suffix with a unique lowercase DNS-safe value such as `r001`, and replace the image with the full digest from step 2. After verifying the target database, migration identity, privileges, credential rotation and backup, create the Job in **Workloads → Jobs**. Wait for **Complete**, check its logs, and resolve any failure before continuing. The database owner then grants `filestats_dashboard` access to the Django-created tables and sequences before the application is deployed. Never put migrations in every web pod's startup. Do not rerun this Job while another migration is running; create a new uniquely named Job after correcting a failure, following database-owner guidance.
6. **Create the application.** After migration succeeds and access restrictions are confirmed, edit `04-app.yaml` with the *same* image digest and, if necessary, the accepted test hostname and allowlist, then create it. The Route includes the requested allowlist at creation. The Service routes to ready web pods; the HTTPS edge Route uses the platform's default certificate unless a certificate is separately configured. Check **Workloads → Deployments/Pods** for a ready pod, inspect events and logs, then browse the test Route. Confirm the browser sees the intended TLS certificate and does not get a redirect loop; test that disallowed networks cannot connect.
7. **Enable autoscaling.** Create `05-hpa.yaml` after the Deployment is ready and resource metrics are available. It starts at 1–3 replicas, 70% of requested CPU, and a 300-second scale-down stabilization window. These values and the Deployment's resource requests/limits are test starting points; measure actual usage and database connections. One replica does not provide high availability. Inspect the HPA's current/desired replicas and metric errors in the console. Do not repeatedly reapply `spec.replicas: 1` from `04-app.yaml` while the HPA is controlling the Deployment.
8. **Test account approval.** Sign in through the sandbox; the account should be pending. Verify the intended first administrator's ORCID iD independently. In the running web pod's **Terminal** tab, an authorized operator can run `python manage.py bootstrap_admin ORCID_ID`; serialize this operation and check the output. Sign in again and use **Administration** to approve a second sandbox account. Test direct admin access with a pending account and test disabling an approved account. Record who performed bootstrap in the platform's operational audit. Configure institutional privileged-access assurance/MFA and recovery before any public release.

## Later releases

Review the new commit and backward-compatible schema changes, and verify the candidate build's exact Git revision. Record the resulting immutable image digest. Back up as required and run a new, uniquely named migration Job with that digest. After it completes, update only the Deployment's container image to the same digest and watch the rollout and application health. The Service, Route and HPA generally do not need recreation. Do not automate image-triggered rollouts ahead of migration. Maintain a tested rollback plan that accounts for schema compatibility and writes after migration; do not expose the old shared-login API to researchers.

Before production: complete and test the dashboard migration and authorization, ORCID end-to-end integration, privileged-user MFA/assurance, HTTPS/proxy settings, security review, backups, resource sizing, DB grants, scaling, logging, alerts and recovery. Test and production require separate credentials and reviewed configuration. The current initial release is not production-ready.
