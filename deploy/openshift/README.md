# OpenShift test deployment

These manifests prepare an **isolated test deployment of the Django foundation**. They do not deploy the existing Express dashboard's features and must not replace its Service or Route. They have not been tested on your cluster. Resource names are fixed to `dashboard-django`; use a separate project or review naming collisions first. Console labels can vary by OpenShift version and role.

## Before starting

- Choose a test project, test hostname and Route access controls with the platform team. A Route can be reachable from the internet as soon as it exists: provision an approved restriction **before** creating it. The application is not ready for public use.
- Confirm that your project allows Git builds, access to GitHub and the image registry, pulling the Dockerfile base image and installing Python packages during a build. Private Git requires an approved build source secret. The Git ref must already be pushed; use an immutable reviewed commit SHA.
- Arrange access to a test PostgreSQL database and obtain reviewed schema ownership and separate migration/runtime logins. The migration login needs DDL privileges for Django-owned tables; the runtime login needs the data and sequence privileges required by Django's account, session and audit tables, without DDL. The database owner must arrange grants, including on new tables and sequences. **Do not run this against production or change collector-owned tables without a reviewed plan.** A backup and restore procedure are required even on a shared test database.
- Register an ORCID sandbox client with exact callback `https://YOUR_TEST_HOST/accounts/orcid/login/callback/`. Use its client ID and secret below; sandbox and production identities/credentials are separate.
- Confirm the Route terminates HTTPS and the router strips untrusted client-supplied `X-Forwarded-Proto` and sets a trustworthy value. Only then enable `DJANGO_TRUST_PROXY_HTTPS`. Without this Django cannot reliably recognize HTTPS behind an edge Route, causing redirects or CSRF failures. If the platform cannot guarantee header trust, use an approved alternative architecture rather than enabling it blindly. Confirm network policies and TLS requirements for PostgreSQL and ORCID with the platform/database owners; these files do not establish database TLS or network isolation.
- Confirm the test hostname is permitted, the cluster can issue/use an appropriate Route certificate, the CPU metrics API and quota are available, and the internal image registry is accessible to application pods. The default Route certificate may not cover an arbitrary hostname.

## Web console: initial release

Select the correct **Project** in every screen. Use the console's **+ / Import YAML** or equivalent YAML editor to paste each file. `kind: List` files create their listed resources; if your console does not support creating a List, create each item separately. These are ordinary resources, not automatically processed templates: edit every `REPLACE_WITH_...` value before creating them. Do not paste filled secrets into an issue or repository.

1. **Create the build.** Edit `01-build.yaml` so `ref` is the chosen pushed commit, then create it. In **Builds → BuildConfigs**, open `dashboard-django`, start a build, and wait for **Complete**. Inspect its logs and the resulting `dashboard-django:candidate` ImageStreamTag. Builds are deliberately manual: pushing to GitHub does not automatically trigger a build or a deployment.
2. **Find the image digest.** In the ImageStream/tag details or its YAML, find the built image's internal registry `dockerImageReference` including `@sha256:...` (typically in the tag's `status.tags[].items[]`). Copy the full digest reference. If the console does not show it, the CLI alternative is `oc -n YOUR_PROJECT get is dashboard-django -o yaml`. Use the same digest for the migration and the application; do not use the mutable `candidate` tag for either release step. Check that the ImageStream belongs to the chosen project.
3. **Set non-secret configuration.** In `02-config.yaml`, replace the hostname in both values with the test Route hostname. Keep `dashboard-probe.local` in `DJANGO_ALLOWED_HOSTS` for internal probes. After the forwarded-header check above, change `DJANGO_TRUST_PROXY_HTTPS` to `1`; create the ConfigMap. Its environment variables are read at pod startup, so later changes require a controlled rollout.
4. **Create Secrets.** Under **Workloads → Secrets**, create three generic/Opaque Secrets. Use the names and keys in `secrets.example.yaml`: `dashboard-django-app`, `dashboard-django-runtime-db`, and `dashboard-django-migration-db`. The two database Secrets must address the same test database, but use their respective runtime and migration roles. Enter actual values directly in the console. Generate `DJANGO_SECRET_KEY` through your approved secret-management process and keep the same value across replicas; never use the example placeholder. Do not commit values or copy production credentials into test. Access to Secrets is sensitive and follows project RBAC.
5. **Run migrations once.** Edit `03-migration-job.yaml`: replace the release suffix with a unique lowercase DNS-safe value such as `r001` and replace the image with the full digest from step 2. Create the Job in **Workloads → Jobs**. Wait for **Complete**, check its logs, and resolve any failure before continuing. Never put migrations in every web pod's startup. Do not rerun this Job while another migration is running; create a new uniquely named Job after correcting a failure, following database-owner guidance.
6. **Create the application.** After migration succeeds and access restrictions are in place, edit `04-app.yaml` with the *same* image digest and test hostname and create it. The Service routes to ready web pods; the HTTPS edge Route uses the platform's default certificate unless a certificate is separately configured. Check **Workloads → Deployments/Pods** for a ready pod, inspect events and logs, then browse the test Route. Confirm the browser sees the intended TLS certificate and does not get a redirect loop.
7. **Enable autoscaling.** Create `05-hpa.yaml` after the Deployment is ready and resource metrics are available. It starts at 1–3 replicas, 70% of requested CPU, and a 300-second scale-down stabilization window. These values and the Deployment's resource requests/limits are test starting points; measure actual usage and database connections. One replica does not provide high availability. Inspect the HPA's current/desired replicas and metric errors in the console. Do not repeatedly reapply `spec.replicas: 1` from `04-app.yaml` while the HPA is controlling the Deployment.
8. **Test account approval.** Sign in through the sandbox; the account should be pending. Verify the intended first administrator's ORCID iD independently. In the running web pod's **Terminal** tab, an authorized operator can run `python manage.py bootstrap_admin ORCID_ID`; serialize this operation and check the output. Sign in again and use **Administration** to approve a second sandbox account. Test direct admin access with a pending account and test disabling an approved account. Record who performed bootstrap in the platform's operational audit. Configure institutional privileged-access assurance/MFA and recovery before any public release.

## Later releases

Review the new commit and backward-compatible schema changes, update the BuildConfig's `spec.source.git.ref` in its YAML, and start a new build. Record the resulting immutable image digest. Back up as required and run a new, uniquely named migration Job with that digest. After it completes, update only the Deployment's container image to the same digest and watch the rollout and application health. The Service, Route and HPA generally do not need recreation. Do not automate image-triggered rollouts ahead of migration. Maintain a tested rollback plan that accounts for schema compatibility and writes after migration; do not expose the old shared-login API to researchers.

Before production: complete and test the dashboard migration and authorization, ORCID end-to-end integration, privileged-user MFA/assurance, HTTPS/proxy settings, security review, backups, resource sizing, DB grants, scaling, logging, alerts and recovery. Test and production require separate credentials and reviewed configuration. The current initial release is not production-ready.
